# Cosmiq OS web

Next.js website and FQLab enquiry prototype. Repository: https://github.com/CosmIQ-OS/cosmiq-os-web (private).
`/demo` is a storyboard; `/pilot-demo` runs a real persisted workflow with a simulated WhatsApp interface.
The catalogue/customer records are sample data, not a live LIMS integration. PDFs remain labelled prototype.

## Local development

Requires Node.js 20.9+ and npm. Copy the relevant settings from `.env.example` to `.env.local` (never commit secrets).

```powershell
npm install
npm run dev
```

Open http://localhost:3000. With `DATABASE_URL` unset, Postgres runs locally through PGlite in `data/pglite`.
For deployment, set a persistent Neon Postgres `DATABASE_URL`; local storage is not suitable for Vercel.
Staff login needs both `STAFF_PASSWORD` and `STAFF_SESSION_SECRET` (32+ characters). `/pilot-demo` also
needs `DEMO_ACCESS_CODE`. Gemini is optional: without `GEMINI_API_KEY`, the keyword parser runs offline.
Production needs HTTPS; larger teams should replace the shared password with individual accounts.

## Enquiry → approved quotation → email

1. Customer requests testing services in a message.
2. Bot collects full name, phone (including country code), and GST number, then compares with records.
3. Requested services are checked against the catalogue; sample type and sample count are collected.
4. Customer explicitly confirms the services/sample summary.
5. Bot asks for the delivery email address, even if an email appeared earlier.
6. A quotation is saved as `pending_approval`. Final chat message: **“Your quotation will be emailed to you after approval.”**
7. Staff sign in at `/staff/quotations`, review identity, staff flags, line items and the PDF, then approve/email or reject with a reason.

An unmatched identity is not silently verified or registered. Staff must acknowledge identity/flags before
approval. Matching entered fields is **not** proof of phone ownership: this prototype does not implement OTP.
Prices/GST/totals are calculated in code from database values, never generated by the AI. There is no
automatic order creation or quotation card in customer chat. Refresh restores the chat in the same browser tab.
Only staff can preview new quotation PDFs or reset the demo; resets are refused while email acceptance is unresolved.

## Email configuration

Create a Resend API key with sending permission and verify your sender domain, then set:

```dotenv
RESEND_API_KEY=your-private-api-key
QUOTATION_EMAIL_FROM=FQLab <quotations@your-verified-domain.com>
```

Without these, approval returns a configuration error and remains pending. Approved emails include the
quotation PDF as an attachment. API credentials are server-only. The queue says **Email submitted** when
the provider accepts; it does not claim inbox delivery. No delivery webhooks are implemented.

Email failures are persisted and expose a staff **Retry email** action. The PDF, sender, recipient and
idempotency key stay identical across retries. A crashed `sending` attempt can be retried after two minutes;
refresh the queue to see it. Retries are refused after 23 hours from approval (Resend's idempotency retention
is 24 hours). Check the provider dashboard before manually arranging another send. There is no automatic
background retry worker. Sending never happens from the customer session.

## Check and test

```powershell
npm run check
npm run build
npx playwright install chromium
npm run test:e2e -- --workers=4
```

Playwright starts a production server on port 3100 and a local HTTP email capture server on 3101.
Tests explicitly clear `DATABASE_URL` and use isolated in-memory PGlite databases; no production data or
real customer inboxes are used. Coverage includes desktop/mobile chat and staff approval, PDF attachment,
identity mismatch, rejection, permissions/CSRF, provider failure, duplicate/concurrent approval, ambiguous
acceptance, crash recovery, expired retry window, reset/seed preservation, pricing and existing lead journeys.
`QUOTATION_EMAIL_TEST_URL` is an internal loopback-only test override and is ignored on Vercel; do not set it
for real sending. Live Resend, Gemini and WhatsApp/LIMS integrations require separate configured testing.

Schema upgrades are additive and run on first database use; legacy records are retained. Chats created
before workflow version 2 must be restarted and cannot expose customer history or bypass phone checks.
Submission commits the quotation, conversation and messages atomically. Reset locks out send claims, and
attempt tokens prevent delayed handlers overwriting newer attempts. New quote numbers use a database
sequence starting at 10000.

## Structure

```text
app/                         # public/staff pages and API routes
components/demo/             # simulated customer phone and lab trace
lib/db.ts                    # Neon/PGlite Postgres entry point
lib/demo/                    # extraction, pure workflow, pricing, records and PDF
lib/quotations/              # approval orchestration, atomic transitions, Resend adapter
lib/staff-session.ts         # signed HTTP-only staff sessions
data/                        # local database (ignored by Git)
tests/e2e/                   # pure/integration rules and desktop/mobile journeys
tests/mock-email-server.mjs  # observable external email boundary for tests
```
